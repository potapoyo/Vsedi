# ADR 0007: 持ち運び可能な環境バックアップと復元

- 状態: 採用
- 日付: 2026-08-10

## 背景

Vsedi は単に現在の PC 上で Git 操作を簡単にするだけでなく、PC の故障・初期化・買い替え後にも VRChat 制作環境を再構成しやすくすることを目指す。

理想的には、新しい PC に Unity Editor、VCC または ALCOM、Git、Git LFS 等の必要ツールを用意し、Vsedi の環境バックアップファイルとアクセス可能なリモートリポジトリがあれば、元の制作プロジェクトを再構成できる状態を目標とする。

ただし、認証情報や OS 固有の絶対 path をそのままバックアップの正本にすると、セキュリティと移植性を損なう。

また、PC の故障は予告なく発生するため、専用の環境バックアップを書き出していなかった場合でも、通常運用で作成される Vsedi の設定ファイルを別媒体等へコピーできていれば、詳しいユーザーが手動で配置して復旧できる余地を残す。

## 決定

Vsedi の設定を次の2種類に分離する。

### 1. アプリ内部設定

現在の PC 上で Vsedi 自身が利用する設定。

例:

- 初回チュートリアル完了状態
- 最近利用したプロジェクト
- UI 設定
- ウィンドウ状態

これらはアプリ専用のローカル設定ファイルとして保存する。初期実装では Tauri Store を利用し、OS 標準のアプリデータ領域へ `settings.json` として保存する。

`settings.json` は通常のファイルとして扱い、OS 標準の Explorer / Finder 等からコピーできる構成にする。

設定ファイルには整数の `schemaVersion` を持たせ、初期値は `1` とする。

```json
{
  "schemaVersion": 1
}
```

### 内部設定ファイルによる手動復旧

専用の環境バックアップが存在しない場合の非常手段として、対応する Vsedi バージョンで利用可能な `settings.json` を OS 標準の所定のアプリデータ領域へ配置した場合、Vsedi が通常の設定ファイルとして読み込める設計を維持する。

これは一般ユーザー向けの推奨復元手順ではなく、設定ファイルの意味と保存場所を理解しているユーザー向けの低レベル復旧手段とする。

- アプリ起動前に所定の場所へ配置できること
- `schemaVersion` を検証すること
- 古い schema は可能な範囲で migration すること
- 未対応 schema や破損した JSON を黙って上書きしないこと
- PC 固有の path が存在しない場合はクラッシュせず、再選択や再登録を促すこと
- credential や秘密情報を `settings.json` に保存しないこと

設定ファイルの復旧は、次の原則に従う。

> 壊れた設定を黙って上書きしない。まず保全し、その後に移行し、最後の手段として再生成する。

具体的には次のように扱う。

- 正常な `settings.json` はそのまま読み込む
- 古い `schemaVersion` で migration 可能な場合は、変換前ファイルを退避してから migration する
- 現在の Vsedi が未対応の新しい `schemaVersion` は読み込みを停止し、元ファイルを変更しない
- JSON が破損している場合は元ファイルを退避し、元ファイルを失わない状態で新しい初期設定を生成できるようにする
- 一部の値だけが不正で安全に既定値へ戻せる場合は、その項目だけ fallback する。ただし元データを破壊的に消さない
- 登録 project の path が存在しない場合は project 登録情報を自動削除せず、「場所が見つからない」状態として保持して再指定を促す

退避ファイルは原因と時刻が識別できる名前とする。例:

- `settings.corrupt-YYYYMMDD-HHMMSS.json`
- `settings.pre-migration-v1-YYYYMMDD-HHMMSS.json`

設定にはトラブルシュート用の非互換判定に使わない参考情報として、最後に書き込んだ Vsedi バージョンを保持してよい。例:

```json
{
  "schemaVersion": 1,
  "lastWrittenBy": "Vsedi 0.1.0"
}
```

`lastWrittenBy` は互換性判定の正本には使用せず、互換性は `schemaVersion` のみで判断する。

この手段は「設定ファイルだけで制作環境を完全復元する」ことを保証しない。リモートに存在するプロジェクトの再取得や Unity / VCC / ALCOM / Git 等の外部環境は別途必要となる。

### 2. 持ち運び可能な環境バックアップ

ユーザーが明示的に export / import できる、Vsedi 独自のバージョン付き JSON ファイルを用意する。

正式なファイル名:

- `vsedi-environment.vsedi.json`

最低限、次のような情報を保存できる設計とする。

- `formatVersion`
- Vsedi バージョン
- 登録プロジェクトの表示名
- リモート URL
- 通常利用する branch
- 必要な Unity version
- VRChat/VPM プロジェクトとしての診断情報
- 使用していた管理ツールの参考情報（VCC / ALCOM 等）
- 復元時に役立つ非秘密情報

初期 `formatVersion` は `1` とする。

## 絶対 path の扱い

旧 PC 上の絶対 path は復元の正本にしない。

保存する場合も「以前の配置場所」という参考情報として扱い、新しい PC ではユーザーが新しい project root / 保存先を選択できるようにする。

`settings.json` を手動復旧した場合も、存在しない旧 PC の絶対 path をそのまま正しい状態とみなさない。

## 秘密情報

環境バックアップには次を含めない。

- GitHub Personal Access Token
- password
- SSH private key
- Git credential helper が保持する秘密情報
- VRChat の認証情報
- VCC / ALCOM の秘密認証情報

復元後に必要な認証は、ユーザーが新しい環境で再設定する。

バックアップファイル単体の漏えいによって、Git hosting や VRChat アカウントが直接侵害される設計にしない。

通常の `settings.json` にも同様の秘密情報を保存しない。

## 復元モード

リモートバックアップ機能が成立した後に「バックアップから環境を復元」する専用モードを実装する。

想定フロー:

1. 環境バックアップ JSON を読み込む
2. `formatVersion` を検証し、必要なら migration を行う
3. Git / Git LFS / Unity / VCC / ALCOM 等の必要環境を診断する
4. 不足しているものをユーザーへ表示する
5. 復元先 directory を選択する
6. リモートリポジトリを clone する
7. Git LFS データを取得する
8. Unity version / VPM 構成を確認する
9. VCC / ALCOM から認識可能なプロジェクト状態か診断する
10. Vsedi にプロジェクトを登録する
11. 復元結果と不足項目を表示する

Vsedi が Unity、VCC、ALCOM 等を自動インストールすることは初期の復元モードの必須要件にしない。まずは必要環境を診断し、揃った環境から安全にプロジェクトを再構成できることを優先する。

## ファイル形式の互換性

### `settings.json`

内部設定には必ず整数の `schemaVersion` を持たせる。

```json
{
  "schemaVersion": 1
}
```

### `vsedi-environment.vsedi.json`

環境バックアップには必ず整数の `formatVersion` を持たせる。

```json
{
  "format": "vsedi-environment",
  "formatVersion": 1
}
```

将来形式を変更する場合は、可能な範囲で旧形式からの migration を実装する。Vsedi のアプリバージョン、内部設定 schema version、環境バックアップ format version はそれぞれ別の概念として扱う。

## 影響

良い点:

- PC 初期化・買い替え時の復旧導線を製品として提供できる
- 専用バックアップがなくても、通常設定ファイルのコピーが残っていれば低レベルな復旧手段を確保できる
- 破損・migration 失敗時にも元の設定ファイルを失いにくい
- 絶対 path や一台の PC に依存しない構成を意識できる
- リモートバックアップの価値が「ファイル保存」から「制作環境の復元」まで広がる
- 秘密情報をバックアップから分離できる

注意点:

- Unity/VPM 周辺の完全な環境再現は外部ツールや配布状況に依存する
- リモートに存在しないローカル専用ファイルは復元できない
- VCC / ALCOM / Unity の仕様変更に追従する必要がある
- settings schema / backup format の migration を長期的に管理する必要がある
- 手動配置された `settings.json` が古い、破損している、または別環境の path を参照している場合は安全に診断する必要がある
- 退避ファイルが蓄積するため、将来必要なら明示的な整理方針を追加する

## 再検討する条件

- 秘密情報まで含む暗号化バックアップへの明確な需要が生じた場合
- Unity / VCC / ALCOM の自動導入まで含める場合
- 複数 PC 間で設定を常時同期する機能を追加する場合
