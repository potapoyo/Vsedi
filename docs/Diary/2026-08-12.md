## 10:00 — GitHub Actions で UI テストを導入する計画

### 指示

- GitHub Actions で UI のテストが出来るようにしたい
- UIのテストが必要なときに実行するようにして、コミット毎に実行するようなことはしない方向としたい
- 日記を記入するルールがあると思いますが、日記を追記出来ますか？

### 方針確認

- 対象プラットフォーム: Windows / Apple Silicon macOS
- テスト実行方法: `workflow_dispatch`（手動トリガー）のみにする
- スケジュール実行: 不要（ユーザーから不要と指示あり）
- テストケース: 外部のJSONファイルで読み込んで柔軟に変更できるようにする
- スクリーンショット: 成功時にも失敗時にも撮影する

### テスト設計案

#### テストケース定義ファイル

```
tests/ui-test-cases.json
```

画面ごとのURL、ナビゲーション操作、アサーション、スクリーンショット設定を宣言的に定義。

例:
```json
{
  "screens": {
    "main": {
      "url": "/index.html",
      "navigations": [],
      "assertions": [
        { "type": "element", "selector": "h1", "text": "Vsedi" },
        { "type": "button", "selector": "button", "text": "フォルダを選択" }
      ],
      "screenshot": {
        "onSuccess": true,
        "onFailure": true
      }
    }
  }
}
```

#### テストランナー

```
tests/run-ui-tests.cjs
```

Node.jsで実装し、テストケースファイルを読み込んで実行。PlaywrightのChromiumを使用してブラウザ操作。

#### GitHub Actions ワークフロー

```
.github/workflows/ui-test.yml
```

- `workflow_dispatch` で手動実行
- 失敗時のスクリーンショットをArtifactとしてアップロード
- 成功時もスクリーンショットを撮影・アップロード

#### スクリーンショット撮影タイミング

| タイミング | 条件 |
|-----------|------|
| 成功時 | 全テストケース毎に撮影 |
| 失敗時 | エラーが発生した画面で撮影 |

### 実装するファイル

1. `tests/ui-test-cases.json` — テストケース定義

## 18:20 — UI テスト実装を CI 実行可能な形へ修正

### 確認結果

- Playwright が依存関係に含まれておらず、CI でテストランナーを起動できない状態だった
- workflow の引数と独自ランナーの引数解釈が一致せず、テストケースを指定すると必ず失敗する状態だった
- button assertion が JSON の selector を使わず、常に画面先頭の button を検証していた
- ブラウザから Tauri の別ウィンドウを開くログテストは、frontend 単体の Playwright テストでは検証できなかった
- 成功時のスクリーンショットが Artifact にアップロードされていなかった

### 修正

- `@playwright/test` を開発依存に追加し、Playwright 標準ランナーへ統一した
- JSON の画面定義を読み込む `tests/ui.spec.ts` を追加した
- `UI_TEST_CASE` により、手動実行時に全ケースまたは指定ケースを選べるようにした
- Vite の起動と終了は Playwright の `webServer` に任せ、Windows と macOS で同じ手順を使えるようにした
- workflow は `workflow_dispatch` のみを維持し、Windows と macOS の matrix で実行するようにした
- 成功時と失敗時のスクリーンショット、失敗時の trace、HTML report を Artifact として保存するようにした
- Tauri native window が必要なログウィンドウ操作は対象外とし、ブラウザで検証可能な基本表示と設定表示をテスト対象にした

### テスト範囲

- この CI は frontend を Chromium で検証する smoke test とする
- native dialog、別ウィンドウ、Rust command、OS integration は Tauri アプリの native test または手動 GUI 確認で扱う

## 20:00 — Windows native UI テストを追加

### 指示

- frontend smoke test に加えて、Windows の Tauri アプリ本体を CI でテストしたい
- `Haprog/tauri-wdio-win-test` を参考にすべきか検討する

### 方針

- 古い WebdriverIO v7 のサンプルを移植せず、Tauri が現在推奨する `@wdio/tauri-service` を使用する
- Playwright の高速な frontend smoke test は残し、native E2E を別の手動 workflow として追加する
- Windows では `external` provider を使用し、Edge WebDriver の整合は Tauri service に任せる
- テスト専用pluginを製品バイナリへ組み込まず、実際のWebView2とRust commandを通る経路を検証する

### 実装

- `.github/workflows/native-ui-test-windows.yml` を `workflow_dispatch` 専用で追加した
- Windows release executable をビルドして WebdriverIO から起動するようにした
- アプリ起動後にRust側の環境診断が完了し、`INTERNAL_ERROR` が表示されないことを確認する
- `ログ表示` 操作でTauriの別ウィンドウが開くことを確認する
- 成功時と失敗時に各テストのスクリーンショットを保存し、Artifactへアップロードする

### テストの役割分担

- Playwright: IPCをモックした高速なfrontend smoke test
- WebdriverIO: Windows実機相当のWebView2、Rust IPC、Tauri windowを通すnative E2E

## 19:55 — UI テストの実行タイミングを整理

### 確認結果

- 通常の `CI` workflow は pull request と `main` への push で動き、typecheck・frontend build・Rust test・生成型の整合性を確認する
- Playwright smoke test は `workflow_dispatch` の手動実行のみで、Windows と Apple Silicon macOS の matrix を実行する
- Playwright は入力が空なら全ケース、ケース名を指定すれば対象ケースだけを実行する
- Windows native test は `workflow_dispatch` の手動実行のみで、Windows release executable を使った native E2E を実行する
- UIテストはコミットごとには実行せず、開発中はローカルコマンド、節目の確認はGitHub Actionsの手動実行で使い分ける

## 20:01 — Windows native workflow の初回実行結果を反映

### 結果

- `main` へマージ後に `Native UI Test (Windows)` を手動実行した
- テスト本体の前に、Node.js 20上でpnpm 11.16.0が `node:sqlite` を読み込めず失敗した

### 修正

- native workflowのNode.jsを22へ更新した
- pnpmもプロジェクト固定値の11.16.0を明示し、通常CIと同じ実行環境に揃えた

## 20:15 — Windows native session 作成失敗を修正

### 結果

- Node.js修正後のworkflowはrelease executableのビルドまで成功した
- WDIO session作成時に `DevToolsActivePort file doesn't exist` が発生し、native test本体を開始できなかった

### 修正

- WebdriverIO capabilityへ `tauri:options.application` とrelease executableの絶対パスを明示した
- service側の `appBinaryPath` と同じパスを使い、driverが起動対象のTauri executableを確実に受け取るようにした

## 20:32 — CI 計画を中断して引き継ぎ

### 対応

- よって、現時点では Windows native test が成功することを確認できていない。Playwright smoke test と native workflow はどちらも手動実行のまま維持し、今回のPRではコード・workflowを変更しない

### 引き継ぎ

- 次回は `main` の `e94483b` 以降を起点に、Tauri 外部 driver の WebView2 セッション起動失敗を調査する
- 調査候補は、`tauri:options.webviewOptions` の明示、Haprog の実績がある WebdriverIO v7 + 手動 `tauri-driver` 起動方式との比較、Windows runner 上での WebView2 user-data-dir / Edge WebDriver の確認
- native test の成功を確認するまで、native workflow を通常CIへ自動組み込みしない

### 結果

- 本エントリのみを引き継ぎ用の変更としてPR化する
- UIテスト CI の追加実装・再実行は中断し、本来の開発へ戻る
